# Upload acknowledgment versus remote readiness

Staging web candidate, October 18, 2026. Not deployed to the website. The patch preserves this web baseline's startup polling and schema-status behavior; the desktop-only startup changes are not part of this port.

A `/auth/sync/status` timestamp proves whether the server has newer data to pull. It never proves that local data was uploaded. `hasRemoteChanges()` retains the early `status_checked` notification for account/billing download readiness, but no longer creates a successful sync result or updates the last successful sync time. Pending-state changes emit `sync_status_changed` after the account-locked check, so Account UI sees the new state.

Before a full sync, `sync-upload-pending=true` is saved under the existing `oa-sync` account-data lock. `_push` encrypts one captured snapshot of all syncable ticket and preference inputs, including preference timestamps. It validates every returned accepted ID against each submitted batch; a missing, duplicate, foreign, or partial acknowledgment fails the pass. Once all batches succeed, `_doSync` checks the live snapshot still matches and saves its SHA-256 fingerprint as `sync-upload-ack`, then clears the pending marker. Interrupted or failed passes retain pending. Both local-only records participate in existing account-scope snapshots; they are not uploaded, logged, or exposed to analytics.

Status checks compare the current snapshot with the acknowledged fingerprint under the same lock. That also catches local mutations followed by exit before the debounce starts, even if the old pending flag was false. Missing acknowledgment on upgrade is unknown/pending until the first confirmed upload. Random encryption IVs, server pull timestamps, and the generated local writer ID are excluded from the fingerprint; all user data carried by that writer's removal snapshot is included. Existing writer records and cryptography are unchanged.

No new redemption-triggered traffic: identity-backed consumption continues to use the existing initial/30-second/foreground reconciliation cadence. Neither batching nor acknowledgment changes the encrypted blob format or migrates oversized archive blobs.

## Bounded upload batches (local follow-up)

`syncUploadBatches.js` preflights every item, then groups requests by both 100 items and **3.5 MiB of exact serialized UTF-8 JSON**, including envelope and commas. It constructs the exact body that is sent. A single item above that bound fails before the first batch is uploaded, retains pending state, and asks for a compatible storage update. It never drops history, splits ciphertext, changes blob IDs, or reports partial acceptance as success. A later HTTP/acceptance failure keeps the whole snapshot pending; retries resend idempotent blob upserts.

The native shell allows **4 MiB only for POST to the exact validated account origin's `/auth/sync`, without a query string**. Other account/billing routes and methods retain 1 MiB; origin validation, session headers, cancellation, and redirect rejection are unchanged. Root and private-candidate implementations are tested.

The signed 0.1.46-sync.2 candidate subsequently uploaded the real wallet in three batches (1,042,877 / 3,285,951 / 3,287,103 bytes; 1 / 2 / 6 items), each HTTP 200. The Account checking-balance banner cleared, billing controls enabled, and the visible count stayed 578. No chat/ticket spends occurred. Runtime pending/accepted-ID internals were not directly inspected; strict acknowledgment and pending persistence are covered by the 52 focused shared tests. The 152 desktop tests passed. These are historical preview results from `deployment/desktop-sync-batched-20261018`. The user subsequently confirmed sync was working. This web port still needs its own release checks and live verification.

Evidence on October 18: the real desktop wallet generated 7,615,909 request bytes across nine items, largest serialized item 3,285,885 bytes. A credential-free synthetic empty-wallet JSON body padded to 4,194,304 bytes was fully uploaded through `chat.openanonymity.ai/auth/sync` and received 401 `unauthorised`, rather than a size rejection. This supports a conservative candidate envelope, **not** an absolute front-door maximum or proof of authenticated storage acceptance. The 512 KiB batching margin is intentional. SSH inspection was unavailable on this follow-up; earlier decoded per-item and item-count server limits remain historical evidence. Authenticated batch results are recorded separately above.

Tests cover pull-success/push-failure, restart and retry, partial/malformed acceptance, an error in a later batch, status during upload, account switching, local mutation before restart, concurrent mutation refusing acknowledgment, and notification timing. Existing isolation, invalidation, and consumption suites remain required. Full release validation and actual cross-device acceptance remain separate from these local tests.
