# Go daemon: inference tickets

The standalone Go module lives in `daemon/`. Its `internal/ticket` package
implements the same public Blind RSA ticket protocol as the browser, without an
account session, browser cookies, or billing credentials. The daemon's local
OpenAI API obtains a fresh provider credential for every request under the
verification policy below.

## Import and invitation redemption

Initialize with `oa-chat init`, then either:

```sh
oa-chat tickets import exported-tickets.json
oa-chat tickets redeem --code-file /path/to/private-invite.txt
```

`tickets redeem` without `--code-file` reads stdin. The file contains only the
24-character invitation code or the OA share URL containing `?tickets=...`.
Keep codes out of command arguments and shell history. Codes generated by the
browser's Share flow use the same issuance path as ordinary invitations.

Import accepts a plain ticket array, `{tickets:[...]}`, active/archived wallet
envelopes, and the `data.tickets` envelope in a full OA backup. Used, consumed,
archived, or invalidated records become local spent tombstones. Finalized token
bytes determine the key generation; mutable imported generation metadata is
discarded. Padding and URL-safe/base64 variations are normalized before
deduplication. A file containing malformed tokens fails without partial import.

Local imports remain usable while the service runs: a process-shared `flock`
coordinates both commands. Finalized wallet records retain only the token and
its global issuer-key fingerprint. Browser blinding and billing/account fields
are not imported. Importing cash-style tickets into another client does not
revoke copies held elsewhere; redeeming the same ticket twice fails upstream.

## Protocol and privacy boundaries

1. Fetch `/api/ticket/issue/public-key` anonymously and check that `key_id`, when
   present, matches SHA-256 of the exact public-key DER encoding.
2. Generate the nonce and blind locally with Cloudflare CIRCL's
   `RSABSSA-SHA384-PSS-Deterministic` implementation. This is the RFC 9578 public
   token variant; the token nonce supplies fresh entropy. The challenge bytes
   exactly match the browser's constant challenge, including empty origin and
   redemption context. Server-provided challenges are never used.
3. Send the code, indexed blinded requests, and `expected_key_id` to
   `/api/alpha-register`. Verify every returned signature while unblinding.
4. Before inference, fetch the live `/chat/model-tickets` map and
   `/chat/pinned-models` availability. Unknown, disabled, malformed, or unpriced
   models fail before selecting tickets. The daemon exposes the remaining
   explicitly priced model IDs in the standard OpenAI model-list envelope.
5. Reserve the required tickets durably, then send only finalized tokens in
   `InferenceTicket token=...` or `InferenceTicket tokens=...` to
   `/api/request_key`.
6. Submit the provisional key and station/org signatures to `/submit_key`.
   A verified credential requires `status=verified`, the exact station ID, and
   the requested key's SHA-256 identifier to match. The deployed verifier and OA
   Chat use the first eight digest bytes (16 lowercase hex characters); a full
   64-character SHA-256 response is also accepted only when all 64 characters
   match. Other lengths, including arbitrary shorter prefixes, fail. Expired,
   pending, unknown, mismatched, malformed and explicit refusal responses
   discard the credential. The narrow [web-compatible outage policy](CLI_ZKAPI.md#privacy-boundaries)
   also applies: eligible unavailable verification is labelled unverified in
   response headers and a fixed foreground warning. This is not blanket
   staging trust. The daemon checks each single-use key once and retains no
   browser-style retry queue. A hard verification failure does not restore
   already spent tickets.

The key identifier is a consistency check on the authenticated HTTPS
`/submit_key` response for that same raw key and signatures, not a standalone
proof or lookup into a broadcast/cache. The verifier validates station and org
signatures over the exact key, then uses its full SHA-256 hash for provider
ownership verification. It deliberately returns the short identifier. This
matches `StationVerifier._hashKey()` and the browser's verifier tests.

The package receives the daemon's configured HTTP transport: direct HTTPS by
default, or TLS-over-Wisp when `relay_url` is nonempty. It clones the client with
no cookie jar and disables redirects. Provider requests use the same transport
mode, while TLS terminates at the inference provider. Direct mode uses local DNS
and exposes the source IP to destination services; blind signatures and fresh
keys do not prevent network-metadata correlation. Opt-in Wisp uses relay-side
DNS and fails closed without direct fallback. Environment proxy variables are
ignored. See [transport configuration](../README.md#build-and-run-ticket-mode).
Requests to the org and verifier contain no prompts, responses, local-client
API keys, request IDs, or account identity. The fixed `OA-Chat/1` User-Agent is
shared by users. Service errors never relay arbitrary upstream error bodies or
credential-bearing transport URLs into logs or client error messages.

## Durability and interrupted operations

The wallet is `tickets.json` under the chosen config directory, mode `0600`.
Wallet saves use a private temporary file, file `fsync`, atomic rename, and
directory `fsync`; the adjacent lock inode is stable across replacements.
Wallets record the exact org origin and cannot silently move between production
and staging configurations.

Issuance records the exact blinded batch and CIRCL's consumed cryptographic
random tape before the first signing request. Retrying the same code after an
outage or process restart reconstructs the original client state and resends
the identical request. The tape stays local and is removed with the code when
the finalized tickets commit. It is never included in an inference token.

Key acquisition removes selected tickets from the available count and records
their spent hashes before transmission. An interrupted/network-failed request
retains an exact reservation. Retry the same model to recover that request
without spending new tickets; another model is blocked until this reservation
is resolved. A definitive rejection or successful issuance closes the
reservation. Verifier failure never refunds consumed tickets. Importing an old
wallet cannot resurrect a spent or reserved token.

Exact-request retries rely on oa-org's atomic replay handling. Issuance recovery
also relies on the pinned CIRCL random-consumption behavior; the regenerated
blinded request is checked against the saved original before finalization.
Never erase an interrupted wallet merely to retry a network failure.

## Validation

`cd daemon && go test -race ./internal/ticket` exercises real RSA issuance and
unblinding, corrupted signatures/challenges, restart recovery, concurrent wallet
instances, spent imports, cookie exclusion, redirect rejection, live model
policy, and verifier station/key binding, including the deployed 16-character
identifier and full-hash/malformed-prefix rejection. When Node.js and the browser vendor
bundle are present, the suite also verifies Go-issued tokens using the browser
Privacy Pass library and browser-issued tokens using Go, including RSA-PSS
public-key DER compatibility. Node.js is not a daemon dependency.

The actual persistent staging org is
`https://org-staging.openanonymity.ai`; the older dotted hostname in historical
build examples does not resolve. Use a separate config directory for staging.
The configured staging verifier remains `https://verifier2.openanonymity.ai`.
On 2026-09-09, the public OA Wisp relay closed connections before the initial
CONTINUE packet. An isolated loopback-only Wisp helper on the existing staging
EC2 host, reached over an SSH local forward, allowed the compiled CLI to redeem
an isolated twelve-ticket invitation through real client-side blinding. This
helper is a test fixture and does not repair the default public relay.
The test relay can observe client connection metadata; destination TLS still
terminates at the provider. Live key issuance succeeded. Initial CLI testing
incorrectly required a full hash and rejected three real verifier approvals
without sending inference content. Inspection of the browser's `_hashKey()`
and oa-verifier's `handleSubmitKey` established that the deployed 16-character
`key_hash` is the intended response contract. The daemon now matches that
contract while retaining exact station, status, and hash checks. Three tickets
were consumed while diagnosing this client compatibility bug; they remain
spent. Live inference results are tracked separately in [CLI validation](../README.md).
